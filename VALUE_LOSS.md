# Value loss: why it spikes and why it does not come down

Diagnosis of the two value-function symptoms seen while training any of the design
hypernetworks (`design_hypernetwork`, `mo_design_hypernetwork`,
`mo_design_predictor_hypernetwork`):

1. `training/v_loss` occasionally jumps by 10-18 orders of magnitude for one epoch and
   then returns to normal;
2. `training/v_loss` often rises during the first third of a run and never settles at a
   small number.

These have **different causes**. (2) is mostly a units artifact and is not by itself a
bug. (1) is a real instability in the value head.

Written to be readable without prior knowledge of the repository.

## 1. Symptom (2): `v_loss` is a squared error in units of (return)^2

`losses.py:222-224` is brax's value loss verbatim:

```python
v_error = vs - baseline
v_loss  = jnp.mean(v_error * v_error) * 0.5 * 0.5
```

`vs` is the GAE(lambda) target — an estimate of the discounted return from each state —
and `baseline` is the value network's prediction. Nothing normalizes either one. So
`v_loss` is reported in units of *squared return*, and its magnitude is set by how large
returns happen to be, not by how good the value function is.

**How large are returns here?** The cheetah's per-objective reward terms
(`cheetah.py:140-144` and `dmcontrol/cheetah.py:133-147`) are

| objective | per-step term | config weight | contribution |
| --- | --- | --- | --- |
| `run` | `min(4, dx/dt)` | 1 | <= 4 |
| `energy` | `-sum(qfrc_actuator[3:]^2)`, and `qfrc = gear * ctrl` with `\|ctrl\| <= 1` | 3e-5 | >= -1.16 |
| `height` | `qpos[1] - default + 0.2` | 10 | order 10 |
| `alive` (shared, added to all three) | 1 | 1 | 1 |

`sparse-heavytail` sampling always includes the three one-hot corners of the simplex
(`grid.py:36-41`), so at every resample the value head is asked to predict the return at
`w = e_run`, `w = e_energy` and `w = e_height`. Reading the per-objective eval returns off
a real run (`l5y2th16`: run 1300, energy 290, height 4800 summed over a 500-step episode)
gives per-step scalarized rewards of 2.6, 0.58 and 9.6. With `discounting = 0.99` and no
early termination the discounted value is `r / (1 - gamma) = 100 r`, i.e.

```
V at the energy corner ~   58
V at the run corner    ~  260
V at the height corner ~  960
```

The instrumented run's `baseline` column saturates at 1188 — the height corner, as
predicted. Two consequences follow directly:

**(i) `v_loss` rises early in training even when nothing is wrong.** The value scale is
set by the policy's performance, and the policy improves. In the table above `baseline`
triples (502 -> 1188) over the run. Since `v_loss` is quadratic in that scale, a *constant
relative* accuracy shows up as a *rising* `v_loss`. And indeed the relative error falls
the whole time while `v_loss` first rises:

```
epoch  1: |verr|/|V| = 90.1/502  = 18.0%   v_loss = 20.7
epoch  6: |verr|/|V| = 132.5/1051 = 12.6%  v_loss = 40.4   <- peak
epoch 17: |verr|/|V| = 76.7/1188 =  6.5%   v_loss = 13.6
```

At the last epoch `v_loss = 13.55` means `rms(verr) = sqrt(4 * 13.55) = 7.4`, against a
value of 1188 — the value function is accurate to about 0.6%. It *has* converged; the
number just does not look like it.

**(ii) The reported `v_loss` is almost entirely the height corner's error.** A squared
loss weights errors by the square of their scale, so the height corner (V ~ 960) enters
the mean with `(960/58)^2 ~ 273` times the weight of the energy corner (V ~ 58). The
gradient the value head receives is therefore dominated by one of the three extreme
tradeoffs, and the low-return tradeoffs are fit almost not at all. This is invisible in
the logged scalar.

**Takeaway.** `v_loss` is not a convergence diagnostic in this setup. The scale-free
version is *explained variance*, `1 - Var(vs - baseline) / Var(vs)`, which is what PPO
implementations normally report and which would have read "fine" through all of the above.

## 2. Symptom (1): the spikes do not come from the environment

A `v_loss` of `1.3e20` means `rms(vs - baseline) ~ 7e9`. Something in the forward pass is
producing numbers of order `1e10`. There are only three candidates: the observations, the
rewards, or the value network's own weights. The instrumented run rules out the first two.

**Observations are bounded, by construction and by measurement.** `_get_obs`
(`dmcontrol/cheetah.py:103-111`) returns `concat(qpos[1:], clip(qvel, -10, 10))` — 17
numbers, of which the 9 velocities are hard-clipped and the 8 positions are a height, a
pitch angle and six range-limited joint angles. `fall_termination` ends the episode as
soon as `|pitch| > 80 deg` or the height drops below `-0.35`, so no state survives long
enough to diverge. Measured: the largest *normalized* observation entering the value
network over the whole run was between 3.7 and 5.9 standard deviations. Nothing here can
produce `1e10`.

**Rewards are bounded, by construction and by measurement.** `run` is capped above at 4,
`energy` is bounded below by `-sum(gear^2) * 3e-5 = -1.16` because the actuators are
`motor`s (`xmls/cheetah.xml:104-111`) and the control is clipped to `[-1, 1]`, `alive` is
exactly 1, and `height` is bounded by the termination condition. Measured: the largest
scalarized per-step reward over the whole run was 16.1.

So the value network is emitting `1e10` from bounded inputs. That can only happen if its
weights are large. The rest of this section is about why they grow.

## 3. Why the value head's weights drift upward without bound

Three properties of the current setup combine. None is a bug on its own.

**(a) The hypernetwork is a bilinear (rank-`num_features`) map, and the loss cannot see
the balance between its two factors.** `DualA2CHypernet.__call__`
(`moppo/networks.py:391-395`, params set up at `:336-372`) computes

```
features = value_mlp(cond)            # cond = [d_norm, w], 4 numbers for cheetah1D
flat_params = features @ value_W + value_b
```

with `value_mlp` a `4 -> 256 -> 256 -> 32` MLP and `value_W` of shape `(32, 5377)` — 5377
being exactly the parameter count of a `17 -> 64 -> 64 -> 1` value MLP. The loss depends
only on the product `features @ value_W`, which is invariant under
`features -> c * features`, `value_W -> value_W / c`. Gradient descent does not preserve
that balance, and there is no term in the objective that prefers any particular one. The
measured columns show both factors growing together: `value_W` from 0.094 to 1.18 (a
factor of 12.6) and the feature MLP from 1.151 to 1.393, while the *generated* value
weights go 4.1 -> 15.1 and are still climbing at the end of the run.

**(b) The gradient never goes to zero, and Adam takes a fixed-size step regardless.** The
target `vs` is a bootstrapped TD(lambda) return, stop-gradiented
(`brax/training/agents/ppo/losses.py:100`). Its residual contains reward noise and
action-sampling noise, so it has an irreducible floor — the value loss cannot reach zero
even in principle. Adam normalizes by the gradient's own second moment, so a persistently
non-zero gradient produces a step of roughly `learning_rate` per coordinate however small
that gradient is, and `optax.adam` has no weight decay to push back
(`mo_design_hypernetwork.py:168-172`). The step budget is large: with
`num_training_steps_per_chunk = 22`, `resamples_per_epoch = 20`,
`num_updates_per_batch = 4` and `num_minibatches = 32`, one logged epoch is
`22 * 20 * 4 * 32 = 56,320` Adam updates. At `learning_rate = 1e-4` a coordinate can move
by up to 5.6 per epoch. The observed drift (about +0.07/epoch on `value_W`) is well inside
that budget.

**(c) Nothing bounds the value output or the value loss.** The value MLP is three affine
layers, so `|V|` grows roughly as the cube of the weight scale times `|obs|`. Taking the
generated weights from 15 to ~150 takes `|V|` from `1e3` to `1e6`, and a single minibatch
then contributes `v_error^2 ~ 1e12`. The squared loss has no cap: there is no value
clipping, no Huber, no target normalization, and `running_statistics.normalize` is called
without `max_abs_value`.

This chain also explains the shape of the spikes in the wandb traces — enormous,
one-epoch-wide, and **self-correcting**. A squared loss on an error of `1e10` produces a
colossal gradient, which drags the weights back within the same epoch. That is why
`l5y2th16` goes `1.3e20 -> 2.5e18 -> 3.3e6 -> 6.8` over four epochs without any
intervention, and why `eval/episode_reward` never dips.

Two secondary factors make the design hypernetworks more exposed than plain PPO, which is
consistent with plain `ppo` runs never spiking:

* The value network's weights are *shared across all designs and tradeoffs* through the
  hypernetwork, so a step taken for one `(d, w)` cell moves the value function for every
  other cell. With `mo_design_predictor_hypernetwork` the design distribution `f(d | w)`
  is itself moving and the grid is redrawn 20 times per epoch, so the conditioning inputs
  are never stationary. Spike frequency tracks this: `ppo` and `design_hypernetwork` never
  spike, `mo_design_hypernetwork` (1 resample/epoch) spikes occasionally,
  `mo_design_predictor_hypernetwork` (20 resamples/epoch) spikes in most epochs.
* `w_variance` defaults to 0 (`networks.py:44,90,168,215`) and no config overrides it, so
  `value_W` and `policy_W` start at *exactly zero*. The hypernetwork therefore starts
  design-agnostic, the feature MLP receives exactly zero gradient on the first update
  (`dL/dfeatures = (dL/dflat) @ W^T = 0`), and all design conditioning has to be bought by
  growing `W` off zero. The growth we are worried about is the same growth the
  architecture requires to work at all.

## 4. Why the spikes are worth fixing even though eval reward keeps rising

`total_loss = policy_loss + v_loss + entropy_loss` and, as noted, `v_loss` is 4-5 orders
of magnitude larger than the other two even in a quiet epoch. Two consequences:

* **The gradient clip is shared.** `optax.chain(optax.clip_by_global_norm(1.0), optax.adam(lr))`
  (`mo_design_hypernetwork.py:168-172`) computes **one** global norm over the whole
  parameter tree, which contains `policy_W`, `policy_b`, `policy_mlp`, `value_W`,
  `value_b` and `value_mlp` together. During a spike that norm is entirely the value
  gradient, so the policy's gradient is rescaled by roughly `1 / ||g_value||`.
* **Adam's second moment is poisoned for ~1000 steps.** A uniform rescaling of the
  gradient mostly cancels in Adam at steady state, but not through a transient: the second
  moment `v` jumps by the square of the spike and relaxes with `beta2 = 0.999` (about a
  1000-step time constant), while the first moment relaxes with `beta1 = 0.9` (about 10
  steps). For the ~1000 updates after each spike, every parameter — policy included —
  takes updates orders of magnitude smaller than intended.

So a spike does not corrupt the policy, it *stalls* it, briefly and invisibly. With spikes
in most epochs that is a persistent brake on learning rather than a catastrophe, which
matches the observation that the eval curve keeps rising but the runs need 1.5e9 steps.

## 5. Fixes, in order of leverage

**1. Put the value target in O(1) units (`reward_scaling`).** The value loss is quadratic
in the return scale and the return scale is ~1000. Setting `reward_scaling = 0.01` in the
`ppo_params` block brings `V` to order 10 and `v_loss` down by `1e4`, which removes both
the "does not converge" appearance and most of the headroom the weights had to grow into.

This is safe for the policy: `normalize_advantage: true` in every config, and
`losses.py:212-213` standardizes the advantages after GAE, so the policy loss is exactly
invariant to a positive `reward_scaling`. Only the value branch sees the change. One-line
config edit, no code change.

**2. Bound the value loss (Huber).** Replace the squared error at `losses.py:222-224` (and
`:114-116`) with `optax.huber_loss`, whose gradient is constant beyond `delta` instead of
growing linearly in the error. This caps what a single bad minibatch can do to Adam's
moments, which is the mechanism in section 4. `delta` should be a few percent of the
return scale (with fix 1 applied, `delta = 1.0` is the natural choice).

**3. Clip the policy and value branches separately.** Split the single
`clip_by_global_norm` into two, masked by the top-level hypernetwork keys (`optax.masked`
with a mask over `policy_*` vs `value_*`), so the value term can no longer scale down the
policy update.

**4. Add weight decay to the hypernetwork.** `optax.adamw` in place of `optax.adam` gives
the bilinear factors of section 3(a) the restoring force they currently lack. (Scaling the
hypernetwork output by `1 / sqrt(num_features)` is a cheaper partial alternative: it fixes
the initial scale but not the drift.)

*Size the decay against the step budget, not the optax default.* `adamw` applies decay as
`-lr * wd * theta` per step, so one epoch of `N = 56,320` updates at `lr = 1e-4` shrinks a
parameter by `exp(-N * lr * wd)`. At the default `wd = 1e-4` that is 0.06% per epoch,
against a measured drift of about `+0.1` per epoch on `value_W`, `value_b` and the feature
MLP. Balancing the two at a magnitude of order 1 needs `N * lr * wd * theta ~ 0.1`, i.e.
**`weight_decay ~ 2e-2`**, about 200x the default. Confirm against actual parameter norms
rather than the max-based proxy used here before fixing a value.

*Exclude `value_b` from the decay.* `value_b` is initialized to the flat init of the target
value network (`moppo/networks.py:369-372`), so it holds that network's hidden layers, not
just an output offset — at init, with `value_W = 0`, the generated network *is* `b`.
Decaying it toward zero degrades toward the all-zero network. Mask it out
(`optax.adamw(..., mask=...)`) or penalize `||b - b_init||^2` instead.

*Why the penalty has to cover both factors.* With `h` the last hidden activations and
`K`, `c` the output `Dense` of `value_mlp` — which has no activation after it
(`moppo/networks.py:32-33`) — the hypernetwork computes

```
features    = h K + c
flat_params = features W + b = h (K W) + (c W + b)
```

so the generated weights split into a conditioning-dependent term `h (K W)` and a constant
offset `c W + b`. `K` and `W` form an exact matrix product `K W` of shape `(256, 5377)` and
rank at most `num_features = 32`. Under the rescaling `K, c -> K/s, c/s` and `W -> s W`,
*both* terms are invariant (`c` and `W` scale oppositely), so the degeneracy covers
everything except `b` — which appears additively and is therefore penalized directly by
ordinary L2, with none of this subtlety. Empirically `b` is not where the magnitude sits:
at the end of the run `max|value_b| = 1.00` against `max|flat_params| = 13.9`, so the
`features W` term dominates by about 14x and is the term that drifts.

It is `K W`, not `||features||`, that sets that term. Penalizing `||features||^2` alone is
therefore not a constraint at all: it
is minimized by `K, c -> 0` with `W -> inf` at fixed `K W`, an infimum of zero reached
without changing the product — and Adam's per-coordinate normalization makes that
relocation essentially free, since it strips out the gradient-magnitude asymmetry between
the two factors. Decaying both factors does constrain the product, exactly:
`min (1/2)(||K||_F^2 + ||W||_F^2)` subject to `K W = M` equals the nuclear norm `||M||_*`.

Two equivalent-or-better variants: penalize the product directly by adding
`lambda * ||value_flat_params||^2` to the loss (more targeted, since that *is* the
generated network); or pin the feature scale architecturally by L2-normalizing or
`LayerNorm`-ing `features` before the matmul, after which all scale must live in `W` and
weight decay on `W` alone becomes a genuine constraint. A feature penalty combined with
either of these works; a feature penalty on its own does not.

**5. Handle the cross-tradeoff scale disparity.** Fixes 1-4 leave the 16x spread between
the energy and height corners intact, so the value head will still fit the height corner
at the expense of the others. The clean fix is to normalize the value target by a running
estimate of the return scale (PopArt), which is a genuine change to the loss. The cheap
approximation is to rebalance `env_config.reward.weights` so the three objectives produce
comparable episode returns — but that changes the physical meaning of the Pareto front, so
it is a modelling decision, not a bug fix.

**6. Log explained variance instead of / alongside `v_loss`.** `1 - Var(vs - baseline) / Var(vs)`
is scale-free and would have read "healthy" through every epoch of the instrumented run.
Two lines in the metrics dict of both loss functions.

Fixes 1, 2 and 6 are small, independent, and target the two symptoms directly; 3 and 4
address the drift; 5 is a separate modelling question.

## 6. Reproducing a spike, and what it refines

Rerunning the instrumented predictor at the **reference config** (`num_envs=4096`,
`resamples_per_epoch=20`, i.e. 56,320 Adam updates per logged epoch rather than 14,080)
reproduces the spike in the second epoch. `sweepV` is the largest `|V|` over a dense
201-point sweep of the design axis crossed with the three simplex corners, evaluated at
zero observation at the *end* of the epoch:

```
     step     v_loss  baseline   verr  reward  normobs  valparams   valW   valb  valmlp  sweepV
 36044800      50.34     635.9   89.2    7.17     5.57      11.91  0.322  0.512   1.150   616.2
 72089600   2.526e4     908.9  156.7    8.80     5.10      14.68  0.503  0.662   1.196   654.9
108134400      31.91    1010.0   87.1   12.87     4.68      11.67  0.585  0.627   1.288   727.6
144179200   1.185e7    7132.0 3854.0   13.17     4.07      12.76  0.696  0.693   1.409   779.0
180224000      38.44    1095.0   72.0   13.07     4.01      12.96  0.787  0.810   1.535   720.7
216268800      33.66    1100.0   55.4   13.11     3.90      13.43  0.866  0.916   1.649   748.8
252313600      10.61    1117.0   59.3   13.37     3.97      13.94  0.928  1.001   1.744   793.3
```

The spikes alternate with full recoveries — `50, 2.5e4, 32, 1.2e7, 38, 34, 11` — and every
recovery epoch returns `baseline`, `verr` and `sweepV` to their trend values. Across the
whole run the largest normalized observation stayed in `[3.90, 5.57]` and the largest
scalarized reward in `[7.17, 13.37]`, spike epochs included.

In the quiet epochs the value function is steadily *improving*: `verr` falls
89 -> 87 -> 72 -> 55 -> 59 against a value scale that settles at ~1100, i.e. from 14% down
to ~5% relative error, and the final `v_loss` of 10.6 is the lowest of the run — exactly
the section 1 picture. Nothing accumulates across the cycle except the hypernetwork's own
weights (`valW` 0.32 -> 0.93, `valb` 0.51 -> 1.00, `valmlp` 1.15 -> 1.74, all monotone
through the spikes as well as the recoveries).

The last row is the clearest single piece of evidence in this document. `v_loss` reaches
`1.2e7`, the value network's own predictions jump 7x (1010 -> 7132) and its errors 44x
(87 -> 3854) — while the largest normalized observation of the entire run, 4.07, occurs in
this very epoch, and the scalarized reward, 13.17, is unremarkable. The inputs got
*quieter* while the outputs blew up. Meanwhile the end-of-epoch design sweep reads 779,
continuing its normal climb, and the generated weights average 12.76, barely above the
quiet epoch before.

Four things this settles:

**(a) The environment is exonerated at the moment of the spike, not just on average.**
In both spike epochs the observation and reward maxima are at or below their quiet-epoch
values (5.10 and 8.80 at `v_loss = 2.5e4`; 4.07 and 13.17 at `v_loss = 1.2e7`, the former
being the smallest observation maximum of the whole run). Whatever drives the spike, it is
not something the simulator fed in.

**(b) The spike is a handful of minibatches, not a global blow-up.** The metrics are
epoch means over all 56,320 minibatches. Write `m_i` for the largest `|v_error|` in
minibatch `i` and `s_i^2` for its mean squared error, so the logged numbers are
`mean_i(0.25 s_i^2) = 25260` and `mean_i(m_i) = 156.7`. Then
`mean_i(s_i^2) = 101,040`, whose square root is **318 — larger than the mean of the
per-minibatch maxima**. Since `s_i <= m_i` always, this forces
`mean(m_i^2) >= 101,040` while `(mean m_i)^2 = 24,555`, hence `std(m_i) >= 277`, about 1.8
times the mean. A distribution whose spread is nearly twice its mean is heavy-tailed: a
few minibatches carry essentially the entire loss. Matching the excess against the quiet
epoch's error statistics puts the peak `|v_error|` somewhere between `1e4` and `1e5`,
against a value scale of ~900.

**(c) It self-corrects inside the epoch and leaves no permanent damage.** By the end of
the spike epoch, `V` swept across the whole design axis is 655 — smooth and normal, barely
changed from 616 the epoch before. So this is not the hypernetwork having been driven into
a globally bad region, and not systematic extrapolation to unseen designs. It is a
transient excursion during optimization that the squared loss immediately punishes and
undoes.

**(d) The recovery is visible in the weights themselves.** The generated value weights
rise into the spike (11.91 -> 14.68) and are then pulled back below their pre-spike level
in the recovery epoch (14.68 -> 11.67), while `v_loss` returns to 31.9 and `sweepV`
continues its normal climb. This is the squared loss acting as its own (violent) regulator:
the excursion produces a gradient large enough to retract the weights, which is why the
runs survive spikes at all. It also means the drift of section 3 is not monotone — it is a
slow upward ratchet punctuated by these corrections.

This **refines section 3** rather than contradicting it. The weight drift is real and
measured (and here runs 4x faster per epoch, 11.9 -> 14.7 in one epoch, tracking the 4x
larger Adam-step budget), and it is what makes the value head progressively more
excursion-prone. But the spike itself is a short, local instability in the value
optimization, not the endpoint of the drift. The distinguishing variable between the run
that spikes and the run that does not is the number of updates per epoch and the number of
design resamples — which is also the ordering seen across algorithms in section 3.

**What would sharpen this further:** log `v_loss` per *resample* rather than per epoch, and
aggregate the diagnostics with `jnp.max` instead of `jnp.mean` (the aggregation is
`jax.tree_util.tree_map(jnp.mean, metrics)` in `training_chunk`). If the spikes cluster in
the first minibatches after a grid redraw — when the value head first meets 64 fresh
`(d, w)` cells and freshly reset environments — the targeted fix is to damp the value
update right after a resample, on top of the general fixes in section 5.

## 7. Confidence

Directly measured, not inferred:

* returns are order 1000 and grow ~2.4x during a run, and `v_loss` tracks that scale while
  the relative value error falls (section 1);
* observations entering the value network stay under 6 normalized units and scalarized
  rewards stay under 17 for an entire run, so neither can produce the observed `1e20`
  (section 2);
* the hypernetwork's `value_W` grows 12.6x and the generated value weights grow 3.7x over
  17 epochs, with no sign of saturating, while `|V|` itself saturated after epoch 8
  (section 3);
* `total_loss == v_loss` to four significant figures in every logged epoch of every
  multi-objective run on disk (section 4).

* a spike reproduces on demand at the reference config, with observations and rewards
  measurably bounded through it, concentrated in a few minibatches, and fully recovered by
  the end of the epoch (section 6).

Inferred, not directly observed: *which* minibatches spike and why that particular update
diverges. Section 6 gives the experiment that would answer it. This does not affect the
fixes in section 5 — every one of them attacks either the return scale or the
unboundedness of the squared loss, both of which are established.
